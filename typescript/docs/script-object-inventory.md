# TS-035E3g-P: bounded offline COFF inventory design

Status: design only, base `903a7e56ef9c081d57662d5bcabb9221d6555389`. No reader has been implemented and no archived object has been parsed or interpreted in this task. Proposed contracts and future expected outcomes are under `docs/validation/ts-035e3g-p/`. Fixture construction, checksums, schema/fixture consistency and preservation checks are the only executable work in this task.

The useful question is narrow: do the 42 byte-identical objects already retained by E3f contain symbol, relocation or directive evidence relevant to the MSVC-object/GNU-driver mixture? A later inventory could expose `_fltused`, section-defined and undefined symbol records, relocations naming those records and raw `.drectve` contents. It cannot prove ABI compatibility, determine which definitions the linker selects, resolve weak/COMDAT semantics, identify actual libraries/DLLs, or establish provenance. Matching names across objects is not a link resolution algorithm.

## Alternatives and decision

| Alternative | Value and limitation |
| --- | --- |
| Keep metadata and source comments only | Already available; cannot distinguish object contents from producer descriptions. |
| Raw string search | Small, but cannot distinguish symbols from debug/data/auxiliary bytes or identify relocation references. |
| Bounded standard COFF inventory | Selected: structural slots and offsets make the dependency question inspectable without executing tools. |
| General object library, disassembler or linker emulation | Unnecessary scope and new trusted dependencies; not proposed. |

The future reader is an evidence-local Node module, not a production API. `contract.d.ts` freezes its closed JSON shapes and pure API. Its archive adapter is separate from the byte reader. The only accepted machine is AMD64 (`0x8664`) in the standard little-endian COFF layout with zero optional-header size. Reject archives, PE images, anonymous/import/bigobj family (`00 00 ff ff`), nonzero line-number fields and extended-relocation flags explicitly. Unknown relocation types are rejected. Unknown symbol storage classes and auxiliary content are retained numerically/as bytes; they are not interpreted. Rejecting a valid but unsupported file is a scope result, not evidence that the producer emitted an invalid object. Do not widen the scope to make the 42 objects pass.

The official format reference is Microsoft's [PE/COFF specification](https://learn.microsoft.com/en-us/windows/win32/debug/pe-format), specifically its COFF header, section table, relocations, symbol/name/auxiliary/string tables, directives and import/archive sections. The design uses 20/40/18/10-byte header/section/symbol/relocation records, signed section numbers, auxiliary slots counted within the symbol table, and length-prefixed strings. Extended relocation markers and short-import signatures are recognized only to reject them. Directive encoding and linker-option interpretation remain outside scope. These are format facts; the conservative acceptance restrictions and limits below are task decisions.

## Exact input boundary

`ordered-inputs.json` is a byte-for-byte copy of the accepted E3f 42-row literal. It is sealed along with its original path/hash reference in `input-links.json`. Preserve order, roles, indexes, exact slash-relative paths, absolute original Windows names, sizes and hashes; no case-folding, path normalization, basename substitution, duplicate row or omitted row. No path supplied by an object or its directives is opened. The separate pure validateBindings(candidate) compares against the sealed literal and returns null or BindingError: first require an array of length 42 (ORDER/null), then each closed row shape and index/role (ORDER/index), exact relative/absolute names (PATH/index), then bytes/hash (IDENTITY/index), in input order. inventoryBoundArchive() takes no path arguments; adapter fault plans require isolated test inputs, never edits to the retained archive. Those 13 plans are followup test requirements, not claimed full malformed-gzip byte fixtures.

The future adapter may read only the accepted E3f inventory and its referenced gzip chunks. Check ordinary canonical ancestry/single-link archive files and sealed compressed bytes before bounded decompression; do not use the original output tree as a fallback. Cap each decompressed chunk at 8 MiB and the reconstructed file at the row's exact size and 16 MiB, then verify chunk and full-file SHA-256. Require archive rows and binding rows to agree, including unique exact paths. Reject missing/extra/reordered bindings, absent chunks, malformed gzip, oversized expansion, wrong lengths or hashes before calling the byte reader. Decompress sequentially and retain only one object plus bounded output at a time. Full prior seals remain authoritative for byte preservation only.

No FFI, subprocess, dynamic import from data, DLL/host library lookup, native dump tool, compiler, linker, disassembler, network fetch, object load or guest execution belongs in the future adapter or reader. This design authorizes none of that, nor the future implementation itself.

## Bounds, interpretation and deterministic failure order

Limits are fixed, not inferred by trying objects: input 16 MiB; sections 4,096; symbol slots 262,144; aggregate relocations 262,144; string table 1 MiB; resolved name 4,096 bytes; aggregate directive bytes 1 MiB; aggregate resolved name bytes 4 MiB (charge every occurrence before allocating it); serialized object JSON 128 MiB. NAME_TOTAL_LIMIT uses the referring name field offset; OUTPUT_LIMIT has null offset and retains input identity. JSON serialization is bounded by the above counts and hex lengths; a later implementation must stream batch entries and never construct an unbounded aggregate. Uint8Array input must have ordinary fixed ArrayBuffer backing; copy once into reader-owned memory. Reject invalid input types before hashing, oversized input before copying/hashing. Such errors have `input:null`; other errors retain complete input size/hash. These limits are conservative refusals, not COFF format maxima.

Check nonnegative safe integer range arithmetic before each slice/read/allocation. Never use wrapping bitwise arithmetic for offsets/count products. A span `[offset, offset+size)` must fit the owned input before reading any field within it. No loops or allocation based on a field before its count limit and total byte span have passed. Error offsets refer to the offending field or beginning of the requested truncated span, not a computed out-of-file address. `rules.json` fixes field order and exact error offsets; first failure only, with no partial Inventory result.

Validation phases are input/type/size; recognized unsupported signatures; complete header; header scope/limits; complete section headers; per-section field/scope checks in index order; symbol/string table extents; occupied-span overlap; section names; primary/auxiliary symbols; relocation records; result construction. Within each phase use ascending record index and the order in `rules.json`. This avoids a parser accidentally reporting a later error for the same fixture.

Sections retain every header field. Raw-size zero requires raw-pointer zero. A nonzero raw size with pointer zero is allowed only when the uninitialized-data flag is set, and then has `rawSha256:null` and no stored bytes; do not synthesize zeros. Relocations on such sections are unsupported. A present raw span must fit the file. Nonempty headers, raw spans, relocation tables, symbol table and string table may not overlap; gaps/trailing bytes are allowed and remain covered by the full input hash, without being interpreted as padding or code. This is a deliberately strict inventory boundary.

Section names use inline bytes or slash plus canonical decimal string-table offset. Reject slash forms with signs, leading zeros (except zero, which then fails offset bounds), whitespace, nondigits, GNU base64 extension or missing NUL padding. Symbol names use inline bytes or the zero-prefix string offset form. String offsets must be at least four and within the declared string-table size, with a NUL before its end. Inline names stop at first NUL and require all remaining name-field bytes zero; exactly eight nonzero bytes need no terminator. Preserve raw name bytes as hex; no UTF-8 replacement, case normalization or display-text equality. A name can point into an existing string's suffix: do not invent a string-boundary restriction. Empty resolved names are allowed and do not match `_fltused`.

Symbol records retain numeric type/storage class/value and signed section number. Positive section indexes must exist; zero maps to undefined when value is zero and common otherwise; -1/-2 map to absolute/debug. Other negative indexes are rejected. These labels describe record fields, not external linkage or whether a definition will satisfy a reference. Auxiliary records stay attached to their owning primary slot as exactly 18 raw bytes each; skip their slots without parsing them as symbols. An auxiliary count that crosses the declared slot count fails. Weak aliases, COMDAT selection and source filenames inside auxiliaries remain uninterpreted.

For relocations, accept numeric types 0–12 only. Type 0 is retained as ignored: width zero, offsetInSection null, and its otherwise-unused symbol/address fields are not dereferenced. For types 1–12 the symbol index must name a primary slot (never an auxiliary slot). Widths are `[8,4,4,4,4,4,4,4,4,2,4,1]`; virtualAddress minus the section's virtualAddress must be nonnegative and the full width must fit stored raw data. Record fields and location are preserved; do not compute a relocation value, addend, target address, or resolved symbol. All types outside this finite set, including pair forms, are unsupported. Reject the overflow flag before touching its sentinel record; both plausible and malformed overflow fixtures must have the same explicit unsupported outcome.

For every section whose resolved name bytes equal `.drectve`, retain section index, offset, exact raw bytes as hex and the INFO-flag boolean, even when the flag is absent. Do not tokenize, decode ANSI, interpret quotes/BOMs, execute directives, infer default libraries, or silently discard NUL/nontext bytes. Names other than the exact bytes are not directive sections. `_fltused` evidence is likewise exact-byte primary-name equality: retain matching slots and nonignored relocation sites referencing those slots. Do not scan arbitrary data or auxiliary records for this name.

## Fixture and implementation review boundary

`fixture-author.mjs` only writes independently specified synthetic bytes at literal offsets and separately authored expected objects; it contains no object reader and never reads the 42 archived objects. `fixtures.json` freezes each complete byte string, input identity and full expected Inventory/Rejected result. The 80 byte fixtures comprise 13 full positive and 67 full rejection literals. Seven invalid-domain constructors and one exact repeated-byte oversize input are separately fixed in input-domain-cases.json. The 94 complete binding negatives and 13 archive fault-injection plans are distinct from parser acceptance. Cases cover header and section truncation, long names/string offsets, every classification, auxiliary slot counting, raw directives, relocation references/widths/overflow, and unsupported signatures. `binding-cases.json` separately freezes complete proposed adapter mutations and expected errors. These are future acceptance literals, not tests that a parser passed.

The design verifier checks fixture serialization/identity/closed shapes and literal preservation only. It does not implement inspectCoff or compare actual objects to the synthetic results. A future task must first implement the exact pure reader and adapter under a new reviewed evidence subtree, run complete literals and negative controls, and return failures without weakening the contract. Only after that task is explicitly authorized to inspect the 42 objects may it produce ordered per-object inventories, retaining each unsupported/error result instead of dropping objects. Any changed scope requires a new design review; no fallback parser or host dump tool.

Full accepted-base preservation is sealed in `preservation.json`: every tracked path at 903a7e56 except root-owned COORDINATION and TASKS, whose accepted prefix is separately preserved. This preservation boundary contains 12,943 tracked files (1,861,812,495 raw checkout bytes); base Git object identities and current raw byte hashes are both recorded. The new TASKS suffix, this new document and the new evidence subtree are the only permitted task changes. The first attempt to invoke the unchanged E3f checker rejected the newly authorized TASKS suffix; boundary-failure.json retains that assertion. The verifier instead reproduces an exact transformed copy of the accepted E3f checker: relocate its paths/imports, and replace only its old empty-suffix check with the exact accepted TASKS prefix plus the sealed new entry. guard-transform.json freezes every replacement/count/hash. All underlying E3f checks remain, and the original verifier is unchanged. No old evidence seal is regenerated. E3e/E3c/E2/E1, all blocked target counts, production interfaces and provenance authority remain unchanged. Stop for actual/root/second review before implementation.


## Correction 1 — bounded batch and absent directive bytes

This versioned correction supersedes only the original one-object/streaming claim and the absent-byte directive ambiguity. Original contracts, fixtures and seals at 19ba0251 remain unchanged; use correction-1/contract.d.ts, rules.json, output-schema.json and fixtures.json for these two corrected rules. All other design requirements remain.

The chosen API is inventoryBoundArchive(): Batch | BindingError with a bounded all-results return, not a streaming API. Retain at most 42 ordered result entries, subject to a fixed 134,217,728-byte budget for the complete UTF-8 JSON.stringify(Batch), with no indentation/replacer/trailing newline and closed fields in declaration order. The empty wrapper is exactly79bytes and includes the closing array/object delimiters. Account wrapper + sum of serialized entry byte lengths + one comma per entry after the first. Every Rejected result is charged identically. Check the next total before appending; equality is allowed, one byte over returns {kind:binding-error,index:currentIndex,code:BATCH_LIMIT}. No partial Batch or later archive reads follow that failure. Validate all bindings first, then per object archive integrity, parsing, and budget accounting in that order. An archive/binding failure therefore precedes budget evaluation; a parsed Rejected that exceeds budget becomes BATCH_LIMIT. After42 entries, require actual serialized total to equal the accounted total and fit the cap.

Memory retains the bounded result tree plus one current object, its bounded result, and serialization scratch. The byte budget measures serialized output, not exact JavaScript heap use; it does not claim constant-memory or one-object-only retention. Per-object limits remain in force. batch-literals.json freezes a full synthetic42-Rejected batch (not actual object findings), exact25343-byte serialization, six exact/one-over budget vectors including final-comma accounting, and three precedence literals. The numerical boundary vectors describe serialized lengths; they are not omitted binary object fixtures.

After section-name resolution and before directive aggregate budgeting, an exact .drectve name with rawSize>0 and rawOffset0 rejects DIRECTIVE_NO_BYTES at sectionHeader+20, regardless of INFO flag. It cannot yield synthetic zeros or a read from offset0. Ordinary BSS retains the original absent-byte behavior. A zero-size .drectve with rawOffset0 remains accepted as an empty directive (offset0,bytes0,hex empty), without slicing the header. Noncanonical raw-pointer states and earlier structural errors retain their original precedence. Three complete new byte/result literals cover INFO on/off absent directives and the genuinely empty case; all80 earlier literals are byte-for-byte preserved as the first80 correction fixtures. No parser is implemented or object interpreted.

The corrected preservation guard verifies the exact19ba0251 document prefix, original files/seals and full accepted-base boundary, permits only the sealed correction TASKS append, and includes correction-1 under its own seal. Source transformations for guard relocation and exact boundary amendments are frozen. Return actual/root/second re-review before implementation.
