# Bounded RegExp literals

Structural Script parsing selects regex scanning when a slash or slash-equals token occurs in primary-expression position. The lexer rescans only its most recent token, before scanning any lookahead into the body. Division remains an ordinary operator, including across newlines. Regex body characters bypass comment, string and template handling, so braces and backticks cannot corrupt the surrounding template state.

Complete literal tokens retain raw pattern and flag text. Supported flags and pattern syntax are validated before any Script executes. Invalid patterns, duplicate/unknown flags and the u/v conflict become pending early errors; the parser certifies the regexp-literal rule only after reaching EOF through the complete supported grammar. A later lexical failure or unsupported grammar prevents that certification. Unterminated lexical forms and non-ASCII flag boundaries remain explicit lex.regexp-literal limitations. Valid but unsupported patterns/modes retain parse.regexp-pattern rather than being called invalid JavaScript.

The AST stores pattern and flag text. Evaluation calls intrinsic RegExpCreate, making a fresh object in the executing code's Realm and ignoring the mutable global constructor. Compilation happens at evaluation and consumes the runtime operation budget; a large valid quantifier in dead code is not expanded during preparation. Certified errors in dynamic Function/eval source become ordinary catchable SyntaxErrors through the existing preparation boundary.

Pattern parsing is now split into a pure syntax module and a runtime adapter. The syntax parser reports invalid/unsupported patterns, a stop request or a depth limit. The runtime adapter preserves the original abrupt completion from its budget callback. Literal validation supplies its own bounded syntax budget without importing runtime objects or constructing a Realm. This also fixes native standalone parser-audit builds: the first version's runtime dependency produced SC2004/SC2009/SC1090 and is retained in build/literal-boundaries-runtime-dependency.json.

The implementation follows [ECMAScript 2025 literal lexical grammar](https://262.ecma-international.org/16.0/#sec-literals-regular-expression-literals) and [literal early errors/evaluation](https://262.ecma-international.org/16.0/#sec-primary-expression-regular-expression-literals), reviewed against [engine262 ExpressionParser at 18cdeb03](https://github.com/engine262/engine262/blob/18cdeb03c363eb31d775648a0d070bdc8a26ced1/src/parser/ExpressionParser.mts). No implementation code was copied.

The isolated suite passes 681 Node guests. Two historical numeric-separator drivers retain their original regex strings with explicit admission assertions; underscores in those bodies are no longer numeric tokens. Those drivers, pattern tests, focused literal tests and the CLI pass both hosts with parsed zero-dynamic coverage. The unchanged C++ regexp-symbol-methods.js reports 45/45 assertions on both hosts. Twelve focused codec checks pass, including exact early-error rule and unsupported-capability boundaries. TS-182's directive guard was propagated with verified baselines and focused Node/native rechecks; full combined canonical acceptance remains pending.

Unicode pattern modes, named groups, lookaround, backreferences and matchAll remain unsupported. Literal admission does not broaden the supported pattern language or parameter grammar.
