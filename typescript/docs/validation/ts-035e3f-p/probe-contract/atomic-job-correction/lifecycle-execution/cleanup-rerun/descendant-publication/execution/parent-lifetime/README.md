# Parent lifetime and ready descendant: proposal only

The 7e1d0e3 failure remains unexplained and unchanged: published PID3272 was not in [28800,568], no leaf-started record existed, and PID568 is unidentified. This design does not relabel that failure. ## Pinned runtime audit

`runtime-audit.json` verifies the pinned Node binary SHA-256, records v26.13.0/libuv1.52.1, and hashes both installed child_process builtin sources. `builtin-source-audit.json` records exact relevant installed lines: default detached normalization, native spawn dispatch and PID propagation. These are host introspection, not a spawned fixture or proof of a native source-to-binary build.

The [libuv1.52.1 Windows source](https://github.com/libuv/libuv/blob/v1.52.1/src/win/process.c#L65-L114) creates a process-owned, noninheritable kill-on-close job. Its [spawn path](https://github.com/libuv/libuv/blob/v1.52.1/src/win/process.c#L1016-L1045) assigns non-detached children after creation, but tolerates access-denied assignment failure. Consequently, immediate parent exit may kill a leaf when assignment succeeded. Neither assignment success nor that causal sequence was measured in the failed attempt. The upstream version match supports a hypothesis, not native binary equivalence or an explanation of member568. [Node's spawn-event contract](https://nodejs.org/api/child_process.html#event-spawn) also distinguishes process creation from successful child execution.

The proposal changes no detachment/breakaway flags or job limits. It does not use unref or parent exit as a workaround in the new live mode. The original descendant mode, including its historical immediate-parent-exit behavior and old leaf keepalive, remains exactly unchanged from `if(mode==='zero')` through end of file. Its prior descendant-left result is not evidence of sustained leaf survival.

| `death-with-live-descendant`, distinct mode `descendant-live` | Keep parent and IPC referenced; wait for closed leaf-ready publication and IPC acknowledgement; independently observe both live members, then kill only the supervisor. | Ready parent and leaf were present before the action, and the independent outer job became empty before fallback. It does not isolate whether the supervisor's job or the parent's libuv job terminated the leaf. |

It does not prove libuv job assignment or establish indefinite survival. |

The first case replaces the intended coverage slot of original ordinal21 with a new ID and mode; it is not a rerun of the old fixture or a retroactive pass. The main plan then contains only unchanged original22–25: three creation timing samples and legacy-gap-control. Original1–20 are not repeated. ## Exact fixture and observer changes

`benign-child.mjs` adds three modes: descendant-live, descendant-exit-diagnostic and leaf-ready. The leaf writes a complete identity record to `.pending`, fsyncs/closes, hard-links it to leaf-ready.json, then sends an IPC readiness message. It retains the same1000ms leaf keepalive as the old fixture so disconnecting IPC cannot itself end the parent-exit diagnostic. This timer is solely process lifetime; no delay gates readiness or schedules the boundary action. The parent validates PID/PPID/token and equality with the closed record, publishes parent-ready.json and the unchanged decimal PID payload/name, and remains referenced. Leaf stderr inherits the already bounded supervisor stderr channel; no new unbounded pipe collector is added.

Spawn, error and premature leaf-exit records retain process IDs, arguments, error name/code/syscall or exit code/signal/readiness state. If error/exit publication itself fails, AggregateError preserves the original event error and the publication error. As before, write/fsync and close failures preserve both original errors when necessary. Every publication is exclusive staging, flush, close and non-overwriting hard-link creation. No alias is deleted. Missing readiness, mismatching identities, premature exit or unavailable hard-link publication remains a diagnostic/harness failure; no fallback, polling retry or longer readiness deadline is introduced.

The harness keeps the literal `descendant not independently present` assertion and the original independent empty-before-fallback assertion. It adds parent membership and closed identity-record checks. The new observer methods open each process with query/synchronize rights, verify exact outer-job membership and live handle state, capture image path and creation FILETIME (as a decimal string), and retain handles until disposal. This supplements PIDs with handle-bound identity. Open/query/wait failures throw and enter the unchanged safety cleanup. Handles do not own a job or keep a process alive. Members enumeration, supervisor KillRoot, outer limits, termination and WaitEmpty logic are unchanged. All three supervisor sources, checkpoint hook, wrapper, contract/environment and stream/pump limits are byte-identical to the preceding approved design. The observer extension is uncompiled.

## Separate diagnostic protocol and outcomes

The diagnostic registers a filesystem watcher before publishing readiness. After the harness has captured live parent/leaf handles, it closes an exclusive request staging file and publishes parent-exit-request.json via non-overwriting File.Move. The watcher validates token/action, closes and publishes parent-exit-intent.json, and calls process.exit(0). A missed watcher notification causes the existing10s bounded parent-exit check to fail; it does not cause a retry or alternate control path. The main live mode has no watcher or exit request.

The harness requires parent-handle termination within10000ms, native exit0, and matching closed intent. It then observes the retained leaf handle for at most10000ms and records one of the two literal diagnostic outcomes in diagnostic-outcomes.json: leaf-exited-after-parent-exit with its original native exit code, or leaf-running-at-deadline-after-parent-exit with null exit code. These are observations, not competing acceptable conformance outcomes. Readiness failure or unexpected parent exit is neither. Process identities and before/after membership snapshots are saved before supervisor termination. The supervisor remains at the original after-resume checkpoint until explicitly killed; its usual root-exit cleanup therefore cannot cause the recorded pre-kill leaf outcome. After saving, the diagnostic kills only the supervisor and requires the original outer empty check. Finally safety cleanup is unchanged on every failure.

Existing main-case deadlines remain unchanged. The separate diagnostic uses the same10s bound for each explicit handle observation and the existing90s supervisor wait; no existing test's limit is increased. No timing sleep is used to hide readiness. Successful diagnostic completion is explicitly `diagnostic-observation-complete`, not matched-future-literal. The raw stderr stream remains subject to existing pump buffering and external-supervisor-death limits; it is not claimed complete after forced death. Closed error/exit files and retained process-handle exit values are the primary additional diagnostics.
