## Concrete fixture mechanism

`benign-child.mjs` retains every original mode, spawn argument, environment, token, started-marker behavior, PID payload, final pathname and parent assertion. Only its fs import and descendant spawn callback change. It opens `descendant-pid.txt.pending` with `wx`, writes exactly `String(child.pid)+'\n'`, calls fsyncSync, and closes the descriptor. Only after successful write, flush and close does linkSync create `descendant-pid.txt` as a hard link to the completed staging file. The child then follows the original unref/exit path. Neither filename is subsequently written or removed by the fixture.

This is a single non-overwriting namespace publication operation on a supported Windows filesystem, not a check-then-rename sequence. The final name cannot expose an open staging writer or a partial copy. Same-directory staging stays on the same volume. Source basis: [Node linkSync and fs APIs](https://nodejs.org/api/fs.html#fslinksyncexistingpath-newpath), [libuv 1.52.1 Windows implementation](https://github.com/libuv/libuv/blob/v1.52.1/src/win/fs.c#L2578), and [Microsoft CreateHardLinkW](https://learn.microsoft.com/en-us/windows/win32/api/winbase/nf-winbase-createhardlinkw). The inspected installed runtime reports Node v26.13.0/libuv1.52.1; this is source/documentation support for the design, not proof from an executed collision or timing test. libuv's Windows link operation calls CreateHardLinkW; its rename path instead uses replacement flags. No rename fallback is proposed.

Hard-link creation adds a name for already completed bytes. Nonreplacement is the link operation's contract, not a preceding existence check. Filesystem support and permissions remain explicit execution uncertainties; the original audit's hard-link EPERM stays preserved and is not dismissed. An unsupported or denied operation must fail and stop review, without falling back to copying, overwriting or retrying. The cooperative installed-tool/OS trust boundary is unchanged; there is no claim against hostile file mutation or power-loss durability.

## Exact errors and cleanup

| Stage | Error behavior | Retained state |
| --- | --- | --- |
| `openSync(...,'wx')` | Original exception propagates; existing staging is not overwritten. | No descriptor acquired by this callback. Existing names remain untouched. |
| Write or fsync | Save the original exception; attempt close exactly once; never link. | Partial or complete staging bytes retained. |
| Close after successful write/flush | Original close exception propagates; never link. | Staging retained; any unresolved native handle is left to process termination, not retried. |
| Write/flush plus close failure | Throw AggregateError with original errors in `[writeOrFlushError, closeError]` order and message `descendant-pid-write-and-close`. | Both original errors retained; no publication. |
| Link | Original Node error object propagates, including native code/path/dest where supplied. A destination collision is an error, never replacement. | Closed staging and any existing destination retained. No unlink or retry. |
| Success | Same PID bytes at published name; original unref/exit follows. | Exactly the staging and published names refer to the same file. |

Any thrown error remains uncaught in the fixture. Existing parent deadlines/assertions and independent outer safety cleanup remain unchanged; there is no new message channel, longer wait or catch-and-retry. Staging evidence is deliberately retained on success and failure. Consequently, future evidence capture must recognize **only** the expected `death-with-descendant/descendant-pid.txt.pending` and `death-with-descendant/descendant-pid.txt` pair as two aliases to one file after successful publication. Record both paths, file identity/link count and equal bytes; preserve partial staging on failure. Do not blindly reuse the earlier archiver's `nlink===1` assertion for this pair, relax old seals, or delete a link to satisfy it. All prior source and archive checks retain their original single-link requirements. This note scopes capture of the new fixture output; it authorizes no execution or broader alias acceptance.
