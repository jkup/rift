# Parser-controlled lexical goals

The lexer now exposes createLexer, whose next method scans one token and whose result method reports the scanned token array and current diagnostic. Repeated EOF requests return the same token. The existing lex and numeric-separator audit functions drain this scanner, retaining their original whole-source behavior. Parser admission is unchanged.

The scanner retains UTF-16 offsets, line/column state and template nesting between requests. Creating it checks the existing source-size limit. A token can carry a lexical failure, as with an unterminated string; the following request returns EOF. Reading result does not scan ahead. Its token array is the scanner's accumulated output, not an immutable snapshot.

This separation prepares for regex literals. ECMAScript selects lexical goals from syntactic context. A primary-expression slash can begin a regex; an operator-position slash means division, even after a newline. Regex bodies must bypass ordinary string, comment and template scanning. A previous-token heuristic cannot distinguish a statement block from an object expression or a control-flow parenthesis from a call.

Before literal admission, replace the parser's whole-parenthesis arrow lookahead with cover parsing. Parse parenthesized contents once, then interpret the result as parameters when followed by an arrow. Otherwise a parenthesis inside a regex body can corrupt lookahead before the parser requests the regex lexical goal. Keep the currently admitted parameter language; destructured parameters are separate work.

Next, connect parser token access to incremental scanning with bounded lookahead and explicit slash rescanning. Preserve token ranges used by declarations, directives and audit evidence. Validate lexical rejection precedence, template substitutions, comments, automatic semicolon insertion and source/depth limits before changing admission. Literal pattern/flag early errors and fresh per-evaluation RegExp objects are another separate step; calling the mutable global constructor is incorrect.

The design follows [ECMAScript 2025 lexical goals](https://262.ecma-international.org/16.0/#sec-ecmascript-language-lexical-grammar), reviewed against engine262 revision 18cdeb03: its [expression parser](https://github.com/engine262/engine262/blob/18cdeb03c363eb31d775648a0d070bdc8a26ced1/src/parser/ExpressionParser.mts) selects regex scanning at primary expressions and uses parenthesized cover parsing; its [lexer](https://github.com/engine262/engine262/blob/18cdeb03c363eb31d775648a0d070bdc8a26ced1/src/parser/Lexer.mts) scans regex bodies separately from ordinary tokens. No implementation code was copied.

The isolated foundation passes exact old/new comparisons for 341 original C++ and TypeScript fixture sources in all three lexer modes: 1023 comparisons of tokens, locations, ranges, diagnostics and rejection objects. Focused expected-result tests pass both hosts at 341 static statements, zero dynamic. Full canonical acceptance follows integration.
